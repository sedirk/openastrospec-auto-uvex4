# ATR585M 下载温度零值的首次保存前复核（0.4.0.205）

## 现场问题与证据边界

2026-09-16，0.4.0.204 的运行 `UVEX-20260915T164438Z-38263651ed034f6`
在科学阶段因 `ATR_SAVED_FRAME_TEMPERATURE_INVALID` 停止。第三次科学尝试
（captureId `fdaebf2320f546c6a54686a2a57bd9e7`）已完成 600 秒曝光并保存；
直接读取原始 FITS，`CCD-TEMP=0`、`SET-TEMP=-10`，而保存后的相机读回为
`-10 °C`、制冷功率 `66%`。该帧光谱和导星连续性检查通过，温度检查未通过，
因此没有进入已接受科学帧计数。

N.I.N.A. 3.2.0.9001 的 `ToupTekAlikeCamera.Temperature` 调用
`sdk.get_Temperature(out temp)`，未检查其成功返回值便使用 `temp / 10.0`。
原生下载路径用此属性填充图像元数据，失败读数可能表现为 0。现场日志在下载附近
还记录了一次相机轮询耗时 6.21 秒的警告，维护期只读状态也曾返回温度 0。
但日志没有那一次 SDK 调用的返回码，不能据此断言第三张当时的真实温度一定是 -10，
也不能把后来读回的温度用于改写既有 FITS。

本轮同时验证了上一版的试拍复用：最终合格的 600 秒 PROBE 原文件作为科学用途引用，
加上一张合格的 600 秒 LIGHT，合计已接受 2/3 张、1200 秒；第三张原始 600 秒仍保留
为温度未通过的尝试。总原始曝光 1800 秒不等于已接受积分 1800 秒。
详见 [科学进度与试拍复用](science-progress-and-probe-reuse-20260916.md)。

## 修复范围

生产实现位于 `AtrTemperatureMetadataConfirmation.cs` 与
`RealObservationStageRunner.TemperatureMetadata.cs`，接入自动观测原有共享采集/保存路径。
前台按钮和后台桥仍调用同一流程，不另建相机采集服务。

仅对已核对的 N.I.N.A. ToupTekAlike 驱动、下载温度精确为 0、实际设定值与本轮目标
相符、目标又不在 0 的正常温度容差内的情况，在**首次保存前**执行只读确认：

1. 从 N.I.N.A. mediator 取得它已经持有的同一 `ICamera`，不创建驱动、不打开相机、
   不重连、不加载第二套 SDK；核对采集身份、当前 owner、连接及 DeviceId。
2. 顺序重新读取实温、实际设定值、制冷开关、能力和功率，使用现有温度验收策略。
   要求连续三次合格；最多六次读取，间隔一秒。只有相同的孤立零温度症状可以补读，
   身份变化、断开、制冷关闭、真实非零升温或其他遥测不合格立即保持原值。
3. 每次原生读取都完整等待；每次返回后检查 12 秒总耗时。这个时限不是对底层 SDK
   的强制抢占，不会遗留仍在访问 owner 的后台读取任务。
4. 通过后，把**最后一次新鲜实测值**写入尚未保存的本帧温度元数据；绝不使用目标温度、
   上一张温度或缓存值代填。失败则保存原来的异常值，仍由原有温度门拒绝。

第一次 FITS 写入同时保留以下来源字段：

| 字段 | 含义 |
| --- | --- |
| `CCD-TEMP` | 原生读数，或已通过确认的本次采集结束后实测温度 |
| `UVEXTN` | 原始下载温度（本问题为 0） |
| `UVEXTSRC` | 确认来源/失败结果代码 |
| `UVEXTUTC` | 成功确认的 UTC 时刻 |
| `UVEXT1`…`UVEXT6` | 本次确认的各次实际温度，包括零值样本 |

完整遥测写入 `atr-temperature-metadata-confirmation` 审计。端点温度复核不是整段
600 秒温度曲线的证明。原始温度、确认来源及时刻也加入帧证据元数据供后续判读。

保存后，若 N.I.N.A. 缓存恰好再次显示同类零温度，采用相同的有界 owner 实温确认，
但仍检查已经落盘的 FITS 温度，不修改文件。良好的新鲜遥测不能覆盖旧文件中的不合格
`CCD-TEMP`。温度、设备身份、曝光身份及其他科学质量门都保留。

本修复没有修改 N.I.N.A. 厂商驱动 DLL、相机固件或 SDK 安装，也没有运行制冷会话
重置脚本。持续遥测失败或真实制冷失效仍须停止科学曝光，不能靠元数据复核放行。
